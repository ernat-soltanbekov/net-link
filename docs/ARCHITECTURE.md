# Как устроен net-link

## Путь одного сообщения

1. Сервер принимает TCP-соединение. Одно из десяти мест резервируется сразу, ещё до получения имени.
2. Горутина чтения получает строки с ограничением длины. Горутина записи отправляет данные в порядке очереди. Обе обслуживают это соединение.
3. После получения допустимого имени клиент входит в `lobby` под блокировкой мьютекса сервера. Сервер фиксирует текущую длину истории и профиль активности, ставит их в очередь отправки и уведомляет остальных о подключении.
4. При получении сообщения горутина чтения захватывает мьютекс, проверяет текст, сохраняет строку с отметкой времени в файл истории комнаты и записывает событие в журнал активности. Счётчики увеличиваются только после успешного сохранения.
5. Сервер помещает одну и ту же неизменяемую строку в очереди остальных участников комнаты. В очередь отправителя это сообщение не попадает. Туда может быть добавлено отдельное личное предупреждение о слишком частой отправке.
6. Мьютекс освобождается. Каждая горутина записи работает независимо, со своим ограничением времени. Переполнение очереди закрывает только соединение соответствующего клиента. Закрытие прерывает его чтение; горутина чтения удаляет участника и уведомляет комнату об отключении.

Два одновременных отправителя конкурируют за один мьютекс. Сообщение того, кто захватит его первым, раньше сохраняется и попадает в очереди. Поэтому все получатели видят одинаковый относительный порядок сообщений. Какой из двух одновременных отправителей окажется первым, заранее не определяется.

## Почему история не конфликтует с текущей перепиской

Отправление с историей содержит открытый файл, зафиксированную длину в байтах и профиль, рассчитанный для этой границы. Горутина записи читает только указанную часть через `io.NewSectionReader`. Чтение выполняется по смещению и не использует общий указатель позиции в файле. Последующие сообщения добавляются через `WriteAt`, начиная со следующего сохранённого смещения. Текущие сообщения попадают в очередь после истории. Файл может расти, но граница чтения не перемещается, поэтому на стыке истории и новых сообщений не возникает пропусков или повторов.

Сообщение, которое не удалось сохранить, не учитывается и не рассылается. Следующая успешная запись начинается с последнего подтверждённого смещения, даже если не удалось обрезать файл после неудачного дополнения. Уже запущенные читатели истории получают только ранее сохранённые части. Два файла не образуют транзакционную базу данных: аварийное завершение, частичная ошибка записи ОС или внезапное отключение питания могут оставить незавершённую запись в журнале активности. Предыдущие сеансы остаются доступными для просмотра; их счётчики не переносятся автоматически в новый сеанс.

Синхронная запись файлов выполняется под мьютексом. Это упрощает проверку порядка операций, однако задержки диска замедляют приём сообщений. Задержки отдельных сокетов изолированы; неблокирующая работа при зависшем хранилище не гарантируется.

## Как рассчитывается активность

`Pace(12, 5)` вычисляет 2,4 и возвращает `quiet`. `Pace(3, 1)` и `Pace(10, 1)` возвращают `active`. `Pace(11, 1)` возвращает `lively`. Перед сравнением результат не округляется.

`TopTalker` один раз обходит словарь счётчиков. Побеждает большее количество сообщений; при равенстве выбирается первое имя в порядке сравнения строк Go. Порядок обхода словаря не влияет на результат. `Summary` только оформляет результаты этих функций. Пустой или недопустимый текст, команды, системные уведомления и личные предупреждения не меняют счётчики.

Детектор частой отправки хранит не более шести отметок времени. При каждом принятом сообщении он удаляет отметки возрастом 30 секунд и больше, добавляет текущее время и проверяет, осталось ли больше пяти отметок. Используется скользящий интервал, а не таймер со сбросом каждые полминуты по часам. Проверка привязана к соединению и продолжает действовать после смены имени или комнаты. Учитываются только принятые сообщения чата.

## Управление ресурсами и завершение работы

- `Server.mu` защищает клиентов, комнаты, счётчики, размер истории и порядок очередей отправки.
- `connection.stopOnce` закрывает сокет и канал `done` ровно один раз.
- `Server.closeOnce` останавливает приём соединений, закрывает все сокеты, дожидается горутин чтения, записи и приёма, затем закрывает файлы истории.
- `log.Logger` упорядочивает запись журнала активности, включая диагностику ошибок ввода.
- `client.Pump` управляет своим соединением и закрываемым потоком ввода; закрытие ввода прерывает ожидающее чтение.
- Только цикл событий gocui обращается к окнам терминального интерфейса. Сетевая горутина чтения дожидается выполнения каждого `Gui.Update` перед следующим обновлением: библиотека не гарантирует порядок независимо отправленных обновлений. Канал исходящих сообщений ограничен по размеру, поэтому ввод с клавиатуры не блокируется сетевыми операциями.

Библиотека интерфейса сама управляет горутинами опроса терминала; интерфейс создаётся один раз на процесс клиента. После потери соединения терминальный клиент остаётся открытым с соответствующим статусом, чтобы пользователь мог прочитать видимую переписку. Ctrl-C завершает работу.

## Порядок изучения кода

Начните с `internal/chatprofile/profiler.go`, затем прочитайте `server/protocol.go`, `server/server.go`, `server/commands.go`, `client/client.go`, `main.go` и, наконец, `client/tui.go`. Тесты объясняют граничные случаи на конкретных примерах переписки. Вспомогательная функция протокольных тестов использует запрос профиля как отметку завершения предыдущих операций: отсутствие эха проверяется по следующему ответу, без произвольной задержки.

Для самостоятельной проверки предскажите содержимое переписки после двух сообщений, смены имени, перехода в другую комнату и повторного подключения. Затем воспроизведите сценарий в трёх терминалах с `nc`. Определите, какая горутина выполняет каждый шаг, и сверьтесь с этим разбором.
